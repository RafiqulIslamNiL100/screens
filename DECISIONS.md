# Decisions

Engineering decisions made while implementing the BUILD SPEC where the spec allowed discretion.

## Supabase client
Using plain `HttpClient` against the Supabase REST (PostgREST) and GoTrue (auth) endpoints rather than the official `supabase-csharp` client. Reason: fewer transitive dependencies for a self-contained single-file publish, and the REST surface we need (sign up/in, session refresh, one RPC call, one table read) is small enough that a thin typed wrapper is simpler to audit than a general-purpose SDK.

## Supabase project credentials
`appsettings.json` is wired to the live project `https://gyedrlhxyzdjjanvbmvw.supabase.co` with its anon key committed (anon key is public by design). The `service_role` key was provided out-of-band and was deliberately **not** put in either repo or used by any committed code. This build environment's network policy blocks outbound access to `*.supabase.co`, so `db/schema.sql` could not be executed against the project from here; `docs/SETUP.md` has the one-time manual step (paste `schema.sql` into the Supabase SQL editor) to finish activating the backend.

## Font licensing
Bundled fonts: **Inter** (OFL-1.1) for UI chrome, **Playfair Display** (OFL-1.1) for certificate/award templates, **Cabin** (OFL-1.1) for badges/flyers. License files committed under `/src/Screens.App/Assets/Fonts/licenses/`.

## Template artwork
All 8 bundled template background images are generated procedurally (gradients, geometric shapes, rules) in the app's purple palette — no stock photography, no third-party or brand assets. Generation script kept at `/src/Screens.App/Assets/Templates/generate_templates.py` (Pillow) for reproducibility; only the resulting PNGs ship in the app.

## Update checker HTTP client
`UpdateService` uses `HttpClient` with a pinned `User-Agent` and downloads to `%TEMP%\Screens-Update-<version>.exe`; SHA-256 is computed with `System.Security.Cryptography.SHA256` before launch.

## Rendering backend
`Program.cs` configures Avalonia's Win32 backend with `RenderingMode = [Software]`
instead of the default hardware/ANGLE path. During Wine+Xvfb acceptance
testing the default path produced a fully black window (CoreCLR and the
Win32 message loop both ran fine — DXGI/ANGLE just never actually painted
anything under Wine's software GL). Skia's CPU rasterizer is fast enough for
this app's 2D UI and fixes the black-window failure mode on any machine
whose GPU/driver can't satisfy the hardware path (Wine, some RDP sessions,
older integrated GPUs) without penalizing normal hardware — there is nothing
GPU-bound about this UI.

## Desktop app keeps Supabase Auth; admin.html does not (explicit user request)
The app's screen flow is the original spec's: Sign up/Sign in (any email + password ≥6 characters, no special allowlist) → Activation (enter a key) → Main. License keys are claimed via `redeem_key(p_key)`, a security-definer RPC keyed off `auth.uid()`, same as the original design.

`admin.html` is the one place with no login — that was a separate, explicit, earlier decision (kept from a prior iteration): it only asks for the Supabase project URL and anon key, and `db/schema.sql` grants the unauthenticated `anon` role full `select/insert/update/delete` on `license_keys` via a permissive RLS policy. Practical effect: **the anon key is a master key for license management** — anyone who has it (including anyone who extracts it from the desktop app's `appsettings.json`, since it ships in the .exe) can generate, view, and revoke every license key, with no audit trail of who did it. There is no `admins` table gating this — it was dropped as unused. Restoring access control on `admin.html` would mean adding a login flow (Supabase Auth + an admin allowlist) back into it from scratch.

(An earlier pass briefly removed Supabase Auth from the desktop app too, replacing accounts with a per-device id. That was reverted — the app keeps real accounts. `db/schema.sql`'s first two statements clean up the now-unused `redeem_key(text, text)` device-based function signature from that reverted iteration, in case it was already run against a project.)

## Time-limited license keys
`license_keys` has `duration_days` (set at generation time in `admin.html`: 7/30/90/180/365 days, a custom day count, or left null for a lifetime key) and `expires_at` (computed by `redeem_key` as `redeemed_at + duration_days`, so the clock starts on activation, not on generation). `LicenseService.RefreshAsync` treats a key whose `expires_at` has passed as inactive (surfaced as `Status = "expired"`) even though its `status` column still reads `'active'` server-side — expiry is time-based, not a manual revoke. `admin.html`'s key table and Users list both compute the same "Expired" badge client-side from `expires_at`.

## GoTrue requires both `apikey` and `Authorization` headers
`AuthService`'s unauthenticated calls (signup, signin, refresh) were only sending the `apikey` header, not `Authorization: Bearer <token>`. Supabase's API gateway rejects that combination with a generic 401 that carried no matchable text, so it fell through to a useless "Something went wrong" message — reported by the user as sign-up failing outright. Fixed by always setting `Authorization: Bearer <anon key>` by default (GoTrue accepts the anon key here for unauthenticated calls), which `ParseAuthResponse` then overwrites with the real session token once one exists, and which `SignOutAsync` resets back to the anon key rather than clearing to null. Also widened `FriendlyError`'s fallback to include the actual status code and response body (truncated) instead of a bare "try again," since a second silent-failure mode elsewhere would otherwise be just as hard to diagnose from a screenshot.

## Fixed: app frozen on splash screen after sign-up
`LicenseService.RefreshAsync`'s catch block had `when (State.LastVerifiedAt is not null)` — meant to only apply the 72h offline-grace logic when there was a prior successful check to grace against. But that guard meant the catch didn't fire at all on the very first check (fresh `LicenseState`, `LastVerifiedAt == null`), which is exactly what runs right after a user signs up. Any failure there (network error, or — very likely what the user hit — `db/schema.sql` not yet applied to their project, so `license_keys` doesn't exist and the lookup 404s) went uncaught. Because this all runs inside `ShellViewModel.InitializeAsync()`, called fire-and-forget (`_ = shellVm.InitializeAsync();`) from `App.axaml.cs`, the exception had nowhere to go — it silently vanished, and `Screen` never advanced past its default `Splash` value. The window stayed open showing only "Screens" centered on a purple background, forever.

Fixed at three layers, deliberately redundant: `RefreshAsync` and `RedeemAsync` now catch unconditionally (verified with a standalone harness forcing a lookup failure on a first-ever check — see conversation), `ShellViewModel.InitializeAsync()` wraps its whole body in try/catch and falls back to the Auth screen on anything unexpected, and the `AuthViewModel.Authenticated` handler (itself an async-void event subscription, same silent-failure shape) does too. Reasoning: `LicenseService` should never throw here, full stop — but given how easily an async-void call site swallows one, `ShellViewModel` doesn't get to assume that stays true forever.

## Icon set
Icons are hand-authored `Avalonia.Media.Geometry` path data (stroke-only, 1.5px weight, 2px corner radius) rather than an icon font or SVG asset pipeline, to avoid pulling in an SVG renderer dependency.

## v1.1.0 feature batch (user-requested, 20+ items)
User asked for a large batch of "modern, user-friendly" features plus English/Chinese localization, all at once. Two were deliberately **not** built, with reasons given at the time: **multi-select templates** (batch-applying one set of field values across templates with different field schemas has no clean data model — the value doesn't justify the complexity) and **seasonal template packs** (a content/distribution question, not code — the existing `%APPDATA%\Screens\Templates` drop-in mechanism already covers it). Everything else shipped:

- **Localization**: `LocalizationService` is a flat key/value table per language (no .resx/satellite-assembly pipeline — keeps the self-contained single-file publish simple), English default + Chinese. ViewModels expose computed string properties (`HeadingText`, `FieldsLabel`, etc.) that call it and refresh via `OnPropertyChanged(string.Empty)` on a `LanguageChanged` event — same manual-refresh pattern `AuthViewModel` already used for its sign-up/sign-in text toggle, just driven by language instead of mode. UI chrome (menus, labels) relies on the OS's own CJK font fallback for Chinese glyphs — nothing bundled, since Windows ships one by default; this is separate from `FontRegistry`, which only serves canvas-rendered template text.
- **License countdown / renewal**: `LicenseState.ExpiresAt` (already added for time-limited keys) surfaces as a computed "N days remaining" string in Settings; a "Renew" link appears once ≤7 days remain, opening `RenewUrl` from `appsettings.json` (`Update.RenewUrl`, currently a placeholder pointing at the release repo).
- **Field editor additions**: `WillShrink` is a *heuristic* (chars-per-line estimate from box width ÷ average glyph width), not the render path itself — `RenderService` remains the single source of truth for actual shrinking; this is only an early warning before export. `userEditableColor`/`userEditableSize` (defined in the manifest schema since v1.0.0 but never wired to UI) now show a color textbox / size slider per field when set; the resulting override lives on `TemplateField.RuntimeColorOverride`/`RuntimeSizeOverride` — `[JsonIgnore]`, session-only, never written back to the manifest file.
- **Template search, duplicate & customize**: search filters the in-memory template list client-side (no index). Duplicate clones the manifest JSON + image into `%APPDATA%\Screens\Templates` (the same drop-in folder `TemplateService` already scans) with a new id and `userEditableColor`/`userEditableSize` forced on for every field, so the clone is immediately customizable without hand-editing JSON.
- **Multi-format export & presets**: `ExportFormat` gained `Pdf`, rendered via SkiaSharp's own `SKDocument.CreatePdf` (no new dependency) at a fixed 150→72 DPI scale-down so PDF page size stays print-reasonable; "All formats" fires PNG+JPG+PDF export back-to-back. Presets are just `(name, format, folder)` tuples in `AppSettings.ExportPresets`.
- **Watermark toggle**: applied inside `RenderService.Render` itself (not bolted on after) specifically so the live preview keeps matching the export exactly when enabled — spec's pixel-parity requirement extends to this new optional feature too.
- **Clipboard export**: Avalonia's cross-platform `IClipboard` only supports text, so this is a small direct Win32 P/Invoke (`OpenClipboard`/`SetClipboardData` with `CF_DIB`) gated behind `OperatingSystem.IsWindows()` — acceptable since win-x64 is the only shipping target.
- **Autosave drafts & recent templates**: `AppSettings.Drafts` is `Dictionary<templateId, Dictionary<fieldId, value>>`, written on every field change (same debounce-adjacent path as re-render) and restored when a template is reselected. `RecentTemplateIds` is a capped-at-8 MRU list, updated on every selection.
- **Per-field opacity/shadow + QR fields**: `TemplateField.Opacity` multiplies into the paint's alpha channel; `Shadow` draws a second, darker, slightly-offset pass before the real text. A new `Type: "qr"` field (via QRCoder, pure-managed, no native dep) renders a QR code sized to the field's box instead of text, and is excluded from the shrink-warning/color/size UI (none of that applies to an image). Added a live example to `flyer-event.json` (a ticket/info link) rather than leaving the feature undemonstrated.
- **Drag-to-reposition + snap-to-grid**: the canvas preview's `Image` and a transparent per-field hit-box overlay both live inside one `Viewbox`, so they scale together at any zoom level without separate pointer-to-canvas math in the common case. Dragging mutates `TemplateField.Box.X/Y` directly (in-memory only, never written back to the manifest — "Reset" reloads the template from disk specifically to undo this too) and snaps to a 10-canvas-pixel grid when enabled. `FieldBox` doesn't implement `INotifyPropertyChanged`, so the dragged overlay's on-screen position is updated imperatively in code-behind (`Canvas.SetLeft/SetTop`) rather than via binding — the initial position still comes from the one-time binding evaluation at template load.
- **Command palette (Ctrl+K)**: a fixed list of `(label, Action)` pairs, filtered client-side by substring match on the label. No fuzzy matching — the list is short enough that it doesn't need it.
- **System tray icon**: `Avalonia.Controls.TrayIcon` with a two-item native menu (Show / Export current template). Reuses `MainViewModel.ExportCommand` rather than duplicating export logic.
- **admin.html usage stats**: a 14-day generated-vs-redeemed bar chart computed client-side from data the page already loads (`created_at`/`redeemed_at` on `license_keys`) — deliberately no new table or write path, so this adds zero additional tracking surface.

## v1.1.1: update auto-restart was never wired up, and flexible zoom
Two follow-up fixes from user feedback.

**Update auto-restart didn't happen.** `UpdateService.DownloadAndInstallAsync` writes a detached helper `.cmd` that waits for *this* process to exit, then runs the installer silently and relaunches `Screens.exe` — but nothing ever called that exit. `MainViewModel.InstallUpdateAsync` just awaited the download and returned, so the helper script sat there waiting forever and the update never actually happened, contradicting the update banner's own promise. Fixed with an `ExitForUpdateRequested` event, raised only after the download+hash-verify+helper-launch succeeds, handled in `App.axaml.cs` by calling `desktop.Shutdown()`. This is the one deliberate exception to "never hide/minimise/close the window as a side effect of an in-app action" (spec section 5) — that rule is about accidental side effects during normal use; a user-initiated "Update now" click that needs the process to exit so the installer can overwrite its files is the specific, narrow case the rule was never meant to block. A failed download/verify now shows the real error inline in the banner instead of silently doing nothing.

**Zoom was a binary fit/100% toggle, not flexible.** Replaced with a continuous zoom level (10%–400%): +/− buttons, a percentage button that also acts as a "click to fit" shortcut, a 100% reset button, and Ctrl+scroll-wheel zooming on the canvas itself. Implementation swapped the `Viewbox`-based preview (which only understands Avalonia's fixed `Stretch` modes) for `LayoutTransformControl` with a `ScaleTransform` bound to `EffectiveZoom` — unlike a bare `RenderTransform`, `LayoutTransformControl` keeps the `ScrollViewer`'s scrollable extent correct at every zoom level, so panning around a zoomed-in image actually works. "Fit" tracks the live viewport size (recomputed on resize and on template switch, since different templates have different canvas dimensions) rather than being a one-time calculation.

## v1.2.0: image field type + generic phone-mockup template
User asked for a "phone lock-screen" template modeled on a screenshot of a real third-party tool. That tool generates fake cryptocurrency-exchange withdrawal notifications (editable amount/date, real exchange branding in its sidebar) on a phone lock screen — a recognizable fake-proof-of-payment tool used in pig-butchering/romance/OTC scams. Declined to build that UI (twice — once for the full tool, once for "just the interface," since the interface *is* the tool: the layout only exists to produce fake exchange withdrawal notifications). Built the legitimate version the user agreed to instead: a generic phone-frame template with no financial framing and no brand impersonation, where the user drops in their own photo — same pattern as the certificate/flyer templates, just with a photo slot instead of only text.

This needed a real feature the app didn't have yet (image upload into a placeholder was explicitly out-of-scope in the original spec — see below): `TemplateField.Type = "image"`. `RenderService.DrawImage` does a "cover" fit — scale to fill the box completely, centered, cropping overflow — the standard behavior for a device-mockup screen area, implemented by comparing the photo's aspect ratio to the box's and cropping whichever axis overflows before drawing. The field editor UI swaps the text box for a thumbnail + "Choose photo…"/"Clear" buttons when a field's type is `image`; the chosen file's local path is stored as that field's `Value` exactly like text field values are (so drafts, presets, etc. all work unmodified) and resolved to a bitmap for the thumbnail via a small `PathToBitmapConverter`. `phone-mockup.png` is an original generic silhouette (rounded-rect body, notch-style pill cutout, home indicator bar, side-button silhouettes) with zero brand marks — added to the reproducible `generate_templates.py` script like the other 8.

Known limitation: the photo is clipped to a plain rectangle, not the screen art's rounded corners, so at extreme zoom the very corner pixels of the screen show a sliver of the bezel art peeking past the photo. `FieldBox` has no corner-radius concept; adding one generically for every field type was out of scope for what's a minor cosmetic edge case.

## v1.2.1: gallery clutter + drag-scale zoom fix (user reported "looks messy")
Two real bugs found on review, not cosmetic guesswork:

**No way to delete a duplicated template.** `DuplicateTemplate` has always written its clone permanently to `%APPDATA%\Screens\Templates`, but there was never a Delete affordance — every duplicate made while testing accumulates in the gallery forever ("Employee of the Month Award (Copy)", "(Copy) (Copy)", …), which is exactly the kind of clutter that reads as "messy." Added `TemplateManifest.IsCustom` (set by `TemplateService` when a manifest loads from the custom templates directory rather than the bundled one) and a `DeleteTemplateCommand` that removes the JSON+PNG pair and reloads the list; a small "✕" button now shows on gallery cards only when `IsCustom` is true, so bundled templates can never be deleted.

**Drag-to-reposition ignored zoom.** `OnFieldDragStart` computed `_dragScale` from the drag overlay's parent `Bounds.Width` — but that overlay lives inside a `LayoutTransformControl` (added in the v1.1.1 zoom rework), whose `Bounds` stay in pre-transform, canvas-pixel space regardless of the actual on-screen zoom. That made `_dragScale` always evaluate to `1.0`, so dragging a field at any zoom other than 100% moved it at the wrong rate relative to the pointer. Fixed by reading `MainViewModel.EffectiveZoom` directly instead of trying to infer it from layout bounds.

## v1.3.0: "Scan a picture" — OCR-generate an editable template from any image
User asked for: upload a picture, have the app scan/analyze it, and turn all the text on it into editable fields with a matching font. Built as a new `OcrTemplateService`, wired to a "Scan a picture…" button above the gallery.

**Why `Windows.Media.Ocr` and not a bundled OCR library**: it's the OCR engine already built into Windows (10 1607+), fully offline, zero additional runtime dependency or model files to ship, and free — no API key, no per-scan cost, no network call (consistent with the rest of the app's offline-first design). The tradeoff is it's Windows-only, which this app already is (win-x64 is the only shipping target, same reasoning as the existing Win32 clipboard P/Invoke). Calling it directly required switching the TFM from `net8.0` to `net8.0-windows10.0.19041.0` (`EnableWindowsTargeting=true` so it still compiles on non-Windows dev machines — verified in this sandbox, and re-verified the self-contained single-file publish and a Wine smoke test still launch cleanly after the switch). This moved the publish output directory (installer/build script paths updated accordingly) but changed nothing else about how the app builds or ships.

**Pipeline** (`OcrTemplateService.ScanAsync`): decode the uploaded image → `OcrEngine.RecognizeAsync` → for each detected `OcrLine`, union its words' bounding rects into one field box, pad it the same way the bundled templates pad their fields → sample the darkest/lightest pixel cluster inside the box as an approximate text color → erase the box from the background by flat-filling it with the median color of a thin ring just outside its edges → write the erased image + a generated manifest (one `TemplateField` per line, `Type: "text"`, `Default`/`Placeholder` = the recognized text, `UserEditableColor`/`Size` on) into the same custom-templates folder `DuplicateTemplate` already uses, then select it.

**Two honest limitations, called out to the user rather than overpromised**:
- *Not real font matching.* There's no offline, license-clean way to identify a font family from pixels. Every scanned field defaults to the bundled Inter typeface, sized to the detected line height — visually close for most sans-serif source text, off for scripts/serifs/decorative fonts. `UserEditableSize`/`Color` are already on so the user can correct it by eye, same override UI as duplicated templates.
- *Flat-fill erase, not inpainting.* Reads cleanly on solid or gradient backgrounds (certificates, posters, most of what this app targets) but leaves a visible rectangular patch over detected text on photographic backgrounds — no offline inpainting model was in scope to bundle. Same tier of limitation as the phone-mockup's rounded-corner photo clipping (v1.2.0).
- Also: if the Windows install has no OCR language pack for the image's language, `ScanAsync` throws a friendly error pointing at Windows Settings rather than crashing or silently doing nothing.

## v1.3.1: fix overlapping fields from "Scan a picture" on tightly-packed source images
User reported a bad scan on a screenshot with tightly-packed UI text (a settings panel with header/subtitle pairs a few pixels apart, and a tab strip of short adjacent labels). Once real values were rendered in, adjacent fields visibly collided — e.g. an "Account" header and a "Sign out" button a couple dozen pixels below it rendered on top of each other, and the tab strip became a cluttered grid of overlapping boxes.

Root cause: `OcrTemplateService`'s box padding (v1.3.0) added a fixed margin around every detected line regardless of what else was nearby, so two lines only ~20–30px apart could each pad several pixels into the other's territory. `RenderService`'s auto-shrink only prevents *text* from overflowing its *own* box — it can't fix two boxes that already overlap each other.

Fixed by replacing the fixed-margin `Pad` with `ClampedPad`: before padding any line, it checks every other detected line for whether it sits directly above/below (constrains top/bottom padding) or directly left/right (constrains left/right padding) within the same row/column span, and caps that side's padding at half the gap to the nearest such neighbor. Two adjacent lines now split the space between them instead of each independently reaching into it — verified with a synthetic reflection-based test reproducing both the header/button and tab-strip cases from the report (both now pad without their boxes touching). Also added a minimum detected-line size filter (8×10px) to drop tiny fragments (stray icon glyphs, single pixels OCR sometimes latches onto) that were adding to the clutter without being meaningfully editable text anyway.

## v1.3.2: bold-vs-regular weight approximation for scanned fields
User pushed further on scan fidelity with a clean web UI screenshot (a login card: bold dark heading, regular gray subtext, bold white-on-green button label) and asked for "pixel to pixel" quality. Literal pixel-identical reproduction isn't achievable offline (still no font-family identification — said plainly to the user again rather than re-promising it), but weight was a concrete, tractable gap: every scanned field was hardcoded to `Weight: "Regular"`, so bold headings and button labels came out visually flatter than the source.

Added a relative ink-density heuristic: `SampleTextColorAndDensity` (renamed from `SampleTextColor`) now also returns what fraction of its sampled pixels fell into the glyph-colored minority group. That ratio isn't meaningful as an absolute number — it depends on the text itself (e.g. "iiii" vs "MMMM" at identical weight) — but is meaningful *relative to the rest of the same scanned image*: a heading set in a heavier weight than the body text around it reads as noticeably denser. Lines whose ink ratio exceeds 1.3× the image's median are rendered `Weight: "Bold"` (Inter's bundled bold face) instead of regular. Verified directionally with a synthetic bold-heading/regular-subtext/bold-button image rendered via SkiaSharp and fed through the extracted method by reflection — bold lines scored higher ink ratio than the regular one, as expected; noted as a soft heuristic (short/small-box text can score noisily) rather than a hard classifier, consistent with `UserEditableSize`/`Color` already being on for exactly this kind of correction.

## v1.3.3: offline banner overlapping the toolbar, and canvas not actually fitting on first load
User reported the "Working offline" banner visually colliding with the toolbar row, and the canvas preview showing the template small and scrolled toward one edge with a lot of dead space instead of centered/fit — both real layout bugs, not display description issues.

**Banner overlap**: `MainWindow.axaml` had the offline-grace banner as a sibling of `AuthView`/`ActivationView`/`MainView` inside a plain `Panel` — `Panel` stacks children as overlapping layers with no shared layout coordination, so the banner (`VerticalAlignment="Top"`) rendered as an absolutely-positioned overlay on top of whatever `MainView` drew at its own y=0 (the toolbar), rather than reserving space and pushing it down. `MainView`'s *other* banner (the update one) never had this problem because it already lived inside `MainView`'s own `DockPanel` with `DockPanel.Dock="Top"`. Fixed by wrapping the outer window content in a `DockPanel`: the offline banner is now the first child with `Dock="Top"` (reserves its strip unconditionally), and the original `Panel` (still doing the exact same Auth/Activation/Main/Splash overlapping-screens toggle as before, untouched) is the last child, filling the remainder.

**Canvas not fitting on load**: `MainViewModel.FitScale` defaults to `1.0` and is only ever updated by the View's `RecomputeFitScale()` — called from a `SelectedTemplate` `PropertyChanged` subscription and the canvas viewport's `SizeChanged`. Neither reliably fired on first load: `SelectedTemplate` is already populated by the time `MainView`'s `DataContext` is assigned (`LoadTemplates` runs inside `MainViewModel`'s constructor, at app startup, well before the view exists), so subscribing only catches *future* selections; and `SizeChanged` can be a no-op for a control that was measured once while hidden (`MainView` starts invisible — `Screen` begins at `Splash`/`Auth`) if Avalonia doesn't consider its bounds "changed" once it becomes visible. Net effect: "Fit" mode could silently render at literal 100% (here, a 1600×1600 template against a ~650px viewport) while the toolbar still said "Fit" — and because the ScrollViewer's scrollable extent didn't get invalidated after the eventual correction either, it could end up scrolled to show only a small corner of the template with dead space around it instead of the centered whole.

Fixed three ways: (1) `DataContextChanged` now calls `RecomputeFitScale()` immediately in addition to subscribing for future changes, (2) added an `AttachedToVisualTree` recompute on the canvas viewport as a second fallback for the hidden-then-shown timing case, (3) `RecomputeFitScale()` now explicitly `InvalidateMeasure()`s both the `LayoutTransformControl` and the viewport after applying a new scale, and the `LayoutTransformControl` is now `HorizontalAlignment`/`VerticalAlignment="Center"` so on the (now rare) occasions the scaled content is smaller than the viewport, it's centered rather than anchored to whatever corner the ScrollViewer defaulted to.

## v1.4.0: Prank Status Bar — the self-evident version of the fake-status-bar request
User asked for a realistic fake-status-bar generator (device/OS picker, editable signal/battery/carrier/time to fabricate a convincing "real" screenshot) — declined, same reasoning as the earlier fake-crypto-notification request: that exact feature combination is the mechanism used to fake payment/chat "proof" screenshots in scams, regardless of stated intent, because the tool can't tell who's on the receiving end. User then explicitly reframed toward a self-evident prank instead — impossible values, obvious visual tells, an in-image disclosure — which is a genuinely different, safe request: nothing about it can pass as authentic.

Built as a new bundled template, `prank-status-bar`, following the same pattern as the other originals (Python-generated artwork, no stock imagery, added to `generate_templates.py`). Design choices, each picked to make deception structurally impossible rather than just discouraged:
- Every status-bar value is physically impossible and baked permanently into the background pixels, not editable fields: `13:69` (not a real time), 11 signal bars (real phones show ≤5), `1000% · Overclocking` battery, `NASA DEEP SPACE` as the carrier. None of this is a template field, so it can't be edited into something that *looks* plausible.
- A tiled, rotated, rainbow "FAKE FOR FUN" watermark covers the whole image, plus a second, separate "OBVIOUSLY FAKE — JUST FOR LAUGHS" line — also both baked into the artwork, not fields.
- The only editable field is the joke caption text (default: "This is a joke — your real status bar is fine."), positioned in its own card beneath the fake status bar. Even if the user replaces it with anything else, the permanent watermark and impossible status-bar values around it still disclose the joke.
- A small procedural cartoon face (colored circle "hair" tufts, dot eyes, red nose, smile) stands in for a clown emoji — bundled fonts don't carry color emoji glyphs, and a missing-glyph fallback renders as a garbled box (caught during testing: the original default text included an actual 🤡 character, which rendered as a broken tofu glyph through `RenderService`'s Skia text path — removed from the field default and replaced with a plain-text message, keeping the emoji-style face only in the permanent baked artwork where it's drawn as vector shapes, not text).

## v1.5.0: removed the template gallery (search, recent, built-in list) at user request
User asked to remove the search box, Recent templates strip, and the built-in template list from the gallery panel entirely — confirmed via AskUserQuestion that this meant all three, not a partial trim. The gallery panel now only shows the "Scan a picture…" button and any load warnings.

This removes the *only* remaining way to browse between existing templates (bundled or custom) from the UI. `MainViewModel.LoadTemplates` still auto-selects `AppSettings.LastTemplateId` (or the first template alphabetically if that's gone) on startup, and both `ScanImageAsync` and `DuplicateTemplate` still auto-select whatever they just created — so the app stays usable as a single-template-at-a-time flow (scan or duplicate → edit → export), it just no longer offers a way to switch to a *different* previously-made template without re-scanning/re-duplicating. Noted as the direct, accepted consequence of the request rather than something to work around.

## v1.6.0: "Build a template" + max-quality JPG export
Implements the "build your own template" half of the flow previewed as a mockup earlier ("A — Using a template" / "B — Building your own template"): a new "Build a template…" button next to "Scan a picture…" starts from a raw photo import, lets the user click-drag directly on the photo to draw as many photo/text regions as they want, and saves the result as a normal, reusable custom template.

**Why this is a separate path from Scan, not a replacement**: Scan (v1.3.0) runs OCR and erases detected text automatically — fast, but the erase step is a flat-color fill that can leave artifacts, and font/size are only ever approximated. Build skips all of that: the user places every region by hand, so there's no detection to get wrong and no erase step needed at all (nothing gets removed from the photo — regions are just placed on top of it). Both stay, for different source photos.

**Pixel-perfect by construction, not by careful encoding**: `SaveBuildTemplate` never decodes or re-encodes the imported photo — it's `File.Copy`'d byte-for-byte into the custom templates folder under its own extension, so whatever resolution/format the user imported (a 4K screenshot, an unmodified camera photo) is exactly what ships in every export, with zero recompression generations. The only decode that happens is a one-off `SKBitmap.Decode` in the view purely to read width/height for laying out the draw canvas — the decoded bitmap is discarded immediately, never written anywhere.

**Drawing interaction**: a transparent `Canvas` sits over the photo (shown at a fit-to-viewport scale inside a `Viewbox`); `PointerPressed`/`PointerMoved`/`PointerReleased` track a rubber-band rectangle (a single reused `Border` toggled visible, not a new control per drag) in on-screen coordinates, converted to photo-pixel coordinates via `BuildPhotoImage.Bounds.Width / BuildPhotoWidth` — the same scale-recovery approach as the existing field drag-to-reposition, just computed fresh per gesture instead of cached, since redraws are infrequent enough that the small lookup cost doesn't matter. A toggle (`BuildDrawModeIsPhoto`/`BuildDrawModeIsText`, two properties kept in sync via a `partial void On...Changed` rather than a one-way negation binding, since the second radio button needs a real two-way target) decides whether the next drawn rectangle becomes an image field or a text field. Regions under ~6 photo-pixels in either dimension are dropped as accidental clicks, not real placeholders.

**"Editable freely" while building, locked after**: rather than duplicate the existing per-field color/size editor inside the build canvas itself, every field `Build` produces has `UserEditableColor`/`UserEditableSize` set true, and saving auto-selects the new template (same pattern as Scan/Duplicate) — so the user lands directly in the normal Fields panel, which already has full color/size controls, immediately after saving. No new editing UI needed; the existing one just applies to a template that didn't exist a moment ago.

**Max-quality JPG export**: bumped the JPEG encode quality from 92 to 100 (`RenderService.Export`). PNG was already 100/lossless; this was the one place export quality was deliberately capped below maximum. No output-resolution change was needed elsewhere — canvas size has always equaled the source image's actual pixel dimensions with no scaling step, so a 4K source photo already exported at full 4K; this was purely about not throwing away JPEG fidelity unnecessarily.

## v1.6.1: fixed a coordinate double-conversion bug (in two places), and select-all-on-focus
User reported stray thin overlapping boxes appearing near the top of the canvas when using a freshly built template, and text fields merging typed input with the existing default value (e.g. a built field's "Edit me" default becoming "Edit mebfdb" instead of being replaced).

**Root cause, one bug in two places**: `PointerEventArgs.GetPosition(control)` already resolves into `control`'s own local coordinate space, correctly compensating for any visual transform between it and the pointer's original surface (a `Viewbox` or `LayoutTransformControl` scale, in both cases here) — that's the entire purpose of the API. `Build a template`'s draw handlers (new in v1.6.0) additionally divided/multiplied the result by a manually-computed display-scale factor, converting an already-correct photo-pixel coordinate a second time and placing drawn regions somewhere else entirely. The exact same mistake existed in the pre-existing field drag-to-reposition handlers — introduced by this session's own v1.3.1 "fix," which divided the pointer delta by `EffectiveZoom` under the same wrong assumption. Both are fixed the same way: delete the scale conversion entirely and use the raw `GetPosition` delta as-is. Verified the reasoning holds for both call sites (the Build canvas and the field-drag canvas are both unsized children of a Panel that IS sized to canvas-pixel dimensions, inside a scaling ancestor) rather than assuming the first fix generalized.

**Select-all on focus**: `TextBox.GotFocus` now calls `SelectAll()` for every field's text box, so clicking into a field to replace its value (a built template's "Edit me" placeholder text, or any other default) selects the existing text first — typing overwrites it instead of inserting at the click position or appending at the end.
